# Threat model

Scope: the Sentinel deployment, meaning the web app and API, the worker, Postgres, the evidence signing key and the anchor key. User funds are out of scope: Sentinel never holds them.

| #   | Threat                                        | Impact                                          | Mitigation                                                                                                                                                                                                                                                                                                                                                                                  | Residual risk                                                                                                                                           |
| --- | --------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **False positive: a transfer flagged FAILED** | Users or ops act on a wrong alarm               | Only an integrity invariant failure produces FAILED. A timeout produces STUCK, which is non-terminal and recovers when evidence arrives. Conflicting observations become anomalies with integrity checks UNKNOWN, never FAILED. Status is persisted only after the evidence a stage needs has been fetched, so a late-submitted old burn isn't reported STUCK before it has been looked at. | Deadlines are heuristics; tune them with `STAGE_DEADLINES_JSON`.                                                                                        |
| 2   | **Malicious or inconsistent RPC data**        | Wrong verdict or wrong evidence                 | Logs are decoded only when emitted by the configured CCTP contract addresses (lookalike events are ignored). Event ABIs are pinned to topic hashes verified on mainnet. The same log observed with different content is an anomaly. Reorged logs are kept, marked `removed`, and excluded from the verdict.                                                                                 | One RPC per chain: a fully lying RPC can hide events (giving STUCK, not a false PASS of a different transfer). Multi-RPC cross-checking is future work. |
| 3   | **Spoofed Iris data**                         | A forged attestation status or message          | Iris data never overrides chain facts. The attested message is checked against the on-chain burn (amount, recipient, domains), and a mismatch is a FAILED invariant rather than being filtered out. Completion requires the destination `MessageReceived` and `MintAndWithdraw` on chain.                                                                                                   |                                                                                                                                                         |
| 4   | **Webhook forgery or replay**                 | A receiver acts on a fake or old event          | HMAC-SHA256 over `${timestamp}.${body}`, constant-time verification, a 5-minute tolerance, unique event ids, and a per-trace monotonic sequence (receivers drop anything not newer). HTTPS only (except localhost), no redirects followed, and a 10 s timeout.                                                                                                                              | Receivers must implement the checks; `verifyWebhook` is the reference.                                                                                  |
| 5   | **Evidence forgery**                          | A fake "proof" attached to a dispute            | Ed25519 over RFC 8785 canonical bytes. Verifiers use the operator's published key (`/.well-known/sentinel-key.json`), never the embedded one. The anchor check recomputes the hash and requires the published registry as the event emitter.                                                                                                                                                | Compromise of the signing key (see 7).                                                                                                                  |
| 6   | **API abuse / RPC credit drain**              | Exhausted RPC quota, denial of service          | Anonymous trace creation is rate limited per client and globally, with counters in Postgres shared across instances. Lookups of existing traces never touch RPC. Privileged endpoints (confirm, anchor, webhook test, `requireAppConfirmation`) need a bearer API key. Client IPs come from `X-Forwarded-For` only with `TRUST_PROXY=true` (rightmost hop).                                 | Read endpoints are not rate limited; put a CDN or WAF in front of a public deployment.                                                                  |
| 7   | **Secret leakage**                            | Leaked RPC keys, signing key or anchor key      | Every logged or persisted error goes through `redact()`, which cuts URLs back to scheme and host (RPC keys live in URL paths) and masks every secret loaded from env. API 500s return only an error id. The web app never holds the anchor key: it only queues jobs. Env parsing errors name variables, never values.                                                                       | Secrets live in env; use a secret manager in production.                                                                                                |
| 8   | **Anchor key compromise or misuse**           | Lost gas funds, junk anchors under our registry | A dedicated, minimally funded key. Worst-case fee and minimum-balance caps (`ANCHOR_MAX_FEE_USDC`, `ANCHOR_MIN_BALANCE_USDC`). Only registry calls are ever sent; there are no transfers. Anchors record the submitter, so verifiers can require the operator's address.                                                                                                                    | Anyone can call the permissionless registry, so verifiers should check `submitter` as well as the emitter.                                              |
| 9   | **Double anchoring or nonce races**           | Wasted gas, confusing duplicate anchors         | A per-account Postgres advisory lock around sign, persist and broadcast. The raw tx is persisted before broadcast and rebroadcast verbatim on crash resume. Replaced nonces are detected and the anchor marked failed.                                                                                                                                                                      |                                                                                                                                                         |
| 10  | **Stale attestations**                        | A transfer looks pending forever                | Per-stage deadlines produce STUCK. Polling slows down but continues, then stops after 7 days with the status preserved.                                                                                                                                                                                                                                                                     | Re-attestation (`/v2/reattest`) is out of scope (no automated recovery).                                                                                |

## Operational guidance

- Rotate `API_KEYS` and `WEBHOOK_SECRET` like any credential. To rotate the evidence key, publish the new public key and keep old bundles verifiable with the old key.
- Monitor `jobs` with `status = 'dead'` and `webhook_deliveries` with `status = 'dead'`.
- Keep the anchor account balance just above `ANCHOR_MIN_BALANCE_USDC`.
